# 产品发布上线流程规范

## 一、发布流程概览

产品的每次版本发布都必须遵循标准化流程，任何绕过流程的"直发"行为均视为违规。整体流程为：需求评审 → 开发 → 测试 → 预发布验证 → 灰度发布 → 正式发布 → 线上监控。

## 二、各阶段与对应环境

- **开发环境**：开发者日常联调使用，代码每提交一次即自动触发构建，不做发布约束。
- **测试环境**：开发完成后合入测试分支，由测试人员在测试环境验证功能、回归缺陷。
- **预发布环境**：与生产环境配置完全一致的"仿真"环境，用于发布前的最后一轮冒烟验证。
- **灰度环境**：正式发布前，先让 5% 的流量（按用户 ID 尾号）进入新版本，验证无异常后再全量。
- **生产环境**：最终线上运行环境，仅在灰度通过后放量。

## 三、上线标准

版本满足以下全部条件，才允许正式上线：

- 测试环境所有测试用例通过，缺陷清单清零或经负责人书面确认可暂缓。
- 预发布环境冒烟测试通过，核心链路（登录、主流程、支付/下单）无阻塞性缺陷。
- 性能压测达标：接口 P99 响应时间不超过 500ms，服务可用性不低于 99.9%。
- 关键变更（涉及数据库表结构、核心接口、安全权限）已由架构评审通过并记录。

## 四、发布窗口

- 常规发布窗口为工作日 20:00 至 22:00，避开业务高峰，便于发布后观察与回滚。
- 紧急修复（高危线上缺陷）不受发布窗口限制，但须由值班负责人审批并全程跟进。
- 每周五 17:00 后与法定节假日前一天，原则上不安排常规发布，避免跨假期无人值守。

## 五、回滚方案

- 每次发布前必须准备上一版本的镜像或制品，并验证回滚步骤可行。
- 触发回滚的条件包括：发布后 15 分钟内核心指标（错误率、响应时间、成功率）出现明显恶化、出现 P0 级线上事故、灰度数据异常。
- 回滚操作须由发布负责人执行，回滚后 30 分钟内进行原因复盘并形成记录。

## 六、审批与责任

- 发布申请由研发负责人提交，经测试负责人、运维负责人、产品负责人三方审批通过后方可执行。
- 发布全程在发布平台留痕，包括提交人、审批人、发布时间、版本号、回滚记录，供事后审计。
- 违反本规范擅自发布的，视情节严重程度，予以通报批评或绩效处罚。
